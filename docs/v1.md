# Runtime and Effect Assurance — Current Scope

Production Agent Systems contains two related execution boundaries:

1. **Agent runtime** — task state, tool schemas, permission decisions, retries for ordinary tools, checkpoints, trace, and replay.
2. **Effect assurance core** — versioned contracts for external operations, a durable SQLite effect ledger, outcome reconciliation, conservative recovery, and deterministic fault-injection tests.

The effect core is optional for each tool. To make a mutating tool use it, attach an `EffectContract` to its `ToolDefinition` and pass an `EffectExecutor` to `AgentRuntime`. A contracted tool cannot execute through the runtime if no effect executor is configured.

## Implemented capabilities

- Explicit task and execution state with validated transitions.
- Structured tool definitions and fail-closed validation for the supported JSON-schema-like subset.
- Runtime permission decisions with trusted, caller-supplied mutation confirmation.
- Provider-neutral planner and model-completion interfaces; this package does not ship a hosted model provider.
- Retry, timeout, and circuit-breaker behavior for ordinary tools.
- Versioned effect contracts, operation-ID conflict detection, stable provider idempotency keys, and request fingerprints.
- Transactional, file-backed SQLite ledger for effect state, dispatch leases, operation results, and ordered effect events.
- Recovery states that distinguish confirmed results from uncertain or quarantined external writes.
- Optional handler timeout with conservative reconciliation. A Python thread timeout does not terminate an already-running remote operation.
- Operator inspection and evidence-backed manual confirmation, rejection, and retry authorization through Python APIs and the local `agent-effect-ops` CLI.
- Deterministic fake-provider fault scenarios and automated tests for lost acknowledgements, provider reconciliation, duplicate suppression, operation conflicts, and recovery.

## Two state stores, two responsibilities

The existing agent task state and checkpoint implementations are in-memory reference stores. The effect ledger is a separate durable SQLite store. The two are not committed in one transaction.

That separation matters: an effect ledger can remember an operation and its provider result, but it cannot atomically commit a payment at a remote provider and a local checkpoint. When the outcome is uncertain, the runtime waits and the effect executor reconciles the provider contract before the same logical action is allowed to continue.

## Security boundary

- Unknown tool arguments are rejected by default, including undeclared fields in nested objects.
- Mutation confirmation is passed by trusted application code through `AgentRuntime.run(..., confirmed_mutations=...)`; task metadata and model output never grant approval.
- The effect executor treats handler timeouts and transport exceptions as uncertain unless provider evidence or a declared idempotency contract makes a retry safe.
- The local operations CLI records an actor, reason, and evidence reference for manual resolution but does not authenticate or authorize the operator itself.

The integrating application remains responsible for identity verification, resource-level authorization, secret handling, least-privilege credentials, and real human approvals. See [security-boundaries.md](security-boundaries.md) and [effect-contracts.md](effect-contracts.md).

## Deliberate limits

- The current effect ledger implementation is SQLite for local and single-host workflows. A PostgreSQL multi-host ledger is not implemented.
- Agent task state, generic trace, and generic audit sink are still in-memory reference implementations. Effect operation events are durable in SQLite, but they are not a complete tamper-evident organizational audit system.
- Provider/framework adapters beyond the standalone contract are not claimed as implemented.
- Universal exactly-once external effects are not guaranteed. They require a cooperating destination or authoritative evidence that lets the caller resolve an uncertain operation.
- The package is not an authentication service, a payment processor, an OS/container sandbox, or a general replacement for durable workflow orchestration.

The CI suite runs without model-provider credentials and never contacts production business systems. A green test run establishes the tested behavior of the library and fake provider—not the safety of every real provider integration.
